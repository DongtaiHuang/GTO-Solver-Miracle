# Account security review

The reviewed boundary is the browser, the same-origin Next.js proxy, FastAPI and a private PostgreSQL database. Google supplies identity assertions. The solver catalog and Trainer's ephemeral game store remain independent of account authentication. Findings below concern the reviewed source and the local tests, not a hosted environment.

| Threat / surface | Potential impact | Protection and residual risk |
|---|---|---|
| Anonymous visitor submits large JSON or expensive queries | Memory, worker or database exhaustion | Previously several public POST routes read the full body before checking size. Both hops now count bytes while reading. FastAPI retains tighter 64 KiB policy limits, a 2 MiB strategy cap and a 1 MiB general cap. Equity and multistreet computations have separate bounded capacity. Production still needs connection, request-rate, duration and concurrency limits. |
| Authenticated user supplies another record ID, owner or imported score | Disclosure, unauthorized writes or corrupted statistics | Owner comes from a validated session; all private reads, changes, lists and nested lookups use owner predicates and bound parameters. Composite keys, transactions, revision checks and original solver-grade verification protect related rows. A missing or foreign scoped object returns the same 404. |
| Another site initiates requests with cookies | Unintended account mutation | Account POST requires the exact configured browser Origin and JSON content type. Host allowlisting is enabled in production. The proxy forwards only cookie, content-type and origin to a configured upstream, permits listed routes and rejects redirects. Forwarded host headers convey no authority. |
| Compromised or copied login cookie | Account access until expiration or revocation | Random opaque secret, server-side digest, eight-hour fixed expiry, HttpOnly, Strict SameSite, account path, Secure on HTTPS. A real unexpired stolen bearer cookie can be used; authentication cannot identify the rightful browser from that cookie alone. Login rotates the existing cookie; logout deletes its row. Account deletion cascades through all its sessions. Account requests serialize on the member row, then recheck and lock the unexpired session. This member-first order coordinates authorized transactions with revocation; a request already authorized may complete before logout commits. |
| Private hand, archive, label or credential submitted as malformed input | Reflected private data, corrupted histories or disclosure of hidden cards | Private validation errors previously inherited framework input echoes. Account schema failures now return a generic 422. Account JSON rejects duplicate keys and nonfinite numbers. Analyzer replay enforces card visibility, observations accept public evidence only, and training import checks the original conditional EVs. React renders labels as text. Tab-local hand and practice archives may contain private study data. |
| Misconfigured proxy or shared browser | Unsafe cookies, exposed routes, previous private records displayed | Task 014A production environment validation, private database network, loopback port publishing, read-only GitHub workflow permissions and non-root application containers. The account page now clears private state after a 401 and reloads on a cross-tab identity-change signal or back-forward-cache restore. The signal contains a random notification ID only. Local tab archives remain available after logout by design; clear them on shared machines. |
| Restore of historical database | Reactivation of old cookies and challenges | Keep restore target disconnected, truncate logins and challenges, and verify both are empty before routing traffic. Native restore equality and invalidation were exercised in Task 014A. |

## Authentication and priorities

The highest-priority code change was bounding request reads on the public path, reachable without a login. Private error redaction, stale account displays and revocation ordering address narrower data exposure windows. No cross-owner record access was identified in the reviewed queries. The severity of any availability issue also depends on the production ingress, which has not been commissioned.

The challenge is browser-bound, random, valid for five minutes and consumed with a transactional DELETE. Invalid credential verification also consumes it. An expired or used challenge is rejected. The login verifies possession of a valid Google identity for the nonce, then uses (issuer, subject) as the account identity. No particular email or user is prespecified by an anonymous challenge. A verified email is optional metadata. The production JWKS URL is fixed, HTTPS, cached by PyJWT and has a four-second timeout. Algorithm and bounded nonempty key ID are now checked before key lookup. Verification restricts RS256, checks signature, exact issuer and audience, authorized party when present, nonce, expiry and issued-at; PyJWT also validates not-before when present. Key-service connectivity failure yields a generic 503. No token values are persisted in browser storage or returned in error details.

Challenge capacity is capped globally. Cache misses and arrivals from many clients can still consume upstream and database capacity. Apply ingress throttling before enabling public sign-in. Database errors use a generic event, hidden SQL parameters and sanitized responses. These controls do not configure logging in an external CDN, proxy, identity service or host.

## Verification and dependencies

Account tests use locally generated RSA keys and a disposable PostgreSQL 16 cluster. Tests exercise wrong signature, issuer, audience, nonce and expiry; key retrieval failure; browser-bound and expired challenges; login rotation and revocation; private error redaction; cross-user persistence; stale revisions; malformed and oversized bodies; host and origin rejection; and availability during database failure. Proxy tests invoke the real Next.js route handler with a mocked upstream and inspect forwarded headers, fixed destination, redirect policy and response cache controls. Full browser runs and the production build are deferred to CI.

Local results: 11 targeted account tests, 354 backend tests with 98.05% combined coverage, 53 frontend tests and 12 numerical tests passed. Ruff, mypy and TypeScript passed. The temporary PostgreSQL process was stopped. No concurrency load test or real Google login was run.

npm audit reported zero known findings for the lockfile. Version-specific PyPI advisory queries covered the installed third-party Python distributions. Findings were limited to pip 23.2.1 and dev-only pytest 8.4.2. Upgraded local pip to 26.3 and pytest to 9.2.0; both replacements returned empty advisory lists. Docker now requests a patched pip and the dev manifest requires pytest >=9.0.3. Package compatibility was checked with pip check. npm ci continues to enforce the existing lockfile. No application dependency calls for custom project install hooks; dependency lifecycle scripts and image bases remain supply-chain trust boundaries. CI adds npm audit at high severity and pip check. Python dependencies are range-based; repeat the advisory audit against the final image. The tracked-file review found no matching private-key files, common token signatures or database dump files. This check is not an exhaustive secret or Git-history scan.

## Task 014D operator checklist

- Register the exact production HTTPS JavaScript origin on the Google **Web** client, configure its audience and inject the client ID server-side.
- Perform live Google sign-in with two dedicated test accounts. Verify rotation, verified identity, distinct saved hands and inability to read, change or delete the other account's fixtures.
- Inspect actual TLS termination, redirect behavior, public host allowlist, cookie scope and Secure/HttpOnly/SameSite attributes. Confirm account cookies, identity assertions and private API responses are never cached or logged.
- Configure ingress limits for login attempts, challenge issuance, concurrent expensive calculations, body size, slow requests and upstream timeouts. Restrict direct backend and database access.
- Inject database credentials through the platform secret manager. Review log redaction, least privilege, secret rotation and recovery access.
- Test logout in multiple tabs, expiry and account deletion. Confirm old sessions fail after committed revocation and restored sessions are cleared before traffic.
- Scan resolved production dependencies and images, run CI build/browser/container jobs and verify the real public URL before approving launch.
